# AGS Red-Team and Threat-Surface Review — 2026-06-09

> Scope: the AGS "structurally impossible, not unlikely" thesis, the runnable enforcer (`examples/enforce.py`), the policy and decision schemas, and the audit model. Private repo, launch-candidate spec.
> Author: Drew Mattie, SaaSquach AI Labs (a division of Charles & Roe Inc.).

## The thesis under test

AGS makes one strong, repeated claim:

> "Every tool call, message send, and delegation is intercepted in deterministic application code before the model's intent reaches the wire. Actions the spine denies are not 'unlikely.' They are structurally impossible." (README)

This review took that claim adversarially. The honest result, up front: **the determinism is real, but "impossible" was overclaimed at the policy, identity, and audit surface.** Taking the model out of the decision path is genuine and valuable, a denied action cannot be reasoned back into existence by a prompt injection. But the gate is only as strong as the policy that feeds it, the identity it trusts, and the audit that records it, and the shipped reference enforcer was bypassable on all three. The README already names this remaining surface ("structural ASR"); this review measures it, and hardens the runnable artifact so the artifact backs the claim instead of undercutting it.

Every finding below was reproduced against the actual code (not reasoned about). The five enforcement and audit bypasses ran against the as-shipped `enforce.py`; the hardened version now passes the same attacker battery.

## Findings

### B1 — Resource matching was unanchored: path traversal and exact-rule-as-wildcard (High)

**Claim attacked:** principle #1, a denied resource is structurally out of reach.

The enforcer matched a rule's resource by stripping a trailing `*` and calling `req["resource"].startswith(prefix)`. Two consequences:

- **Path traversal.** A rule allowing `read kb/*` (prefix `kb/`) granted `read kb/../../etc/shadow`, because the string still starts with `kb/`. The allowed scope could be escaped with `..`.
- **Exact rules behaved as wildcards.** A rule with resource `kb/pricing` (no trailing `*`) matched by prefix, so it also granted `kb/pricing-CONFIDENTIAL`. Every exact rule was silently a `prefix*` rule.

**PoC (as-shipped code):**
```
traversal  read kb/../../etc/shadow            -> allow   (escapes kb/ scope)
exact rule kb/pricing, req kb/pricing-CONFID.. -> allow   (over-grant)
```

**Fix (applied):** resources are canonicalized (any `..` or `.` segment is denied outright), prefix rules match on a segment boundary (`kb/*` matches `kb` and `kb/x`, not `kbsecrets`), and exact rules match by equality only.

### B2 — First-match-wins let an allow shadow a later deny (High)

**Claim attacked:** principle #1 determinism, and the policy-as-code review story (principle #4).

The enforcer returned on the first matching rule regardless of effect. A broad allow ordered before a narrow deny meant the deny never fired. Rule order was load-bearing and undocumented, so a correctly-written deny silently failed open if a policy author placed it after the allow it was meant to constrain. The policy engines AGS cites (OPA, Cedar) make explicit deny override allow regardless of order, precisely to remove this footgun.

**PoC (as-shipped code):**
```
policy: [allow research read kb/*,  deny research read kb/secrets]
request: read kb/secrets  ->  allow (matched allow-broad)   # deny never fires
```

**Fix (applied):** deny-override semantics. Every rule is evaluated; any matching explicit deny wins over any allow regardless of order; then default-deny.

### B3 — Privilege rings were recorded but never enforced (High)

**Claim attacked:** principle #5, "low-trust agents cannot reach high-trust resources by accident or by design."

The request carried `ring`, rules carried `ring_max`, the audit record carried `principal.ring`, and the four-ring model is documented in `examples/privilege-rings.md`. But the enforcer never compared them. A sandboxed (Ring 3) agent passed a rule whose ceiling was Ring 0 exactly as easily as a Ring 0 agent. The single most concrete control in the spec was decorative in the artifact that demonstrates it.

**PoC (as-shipped code):**
```
rule: allow ops-agent notify channel:internal ring_max 2
request: ops-agent at ring 99  ->  allow   # ring ignored
```

**Fix (applied):** an allow with `ring_max R` grants only to a request at `ring <= R` (Ring 0 = most privileged), failing closed when the ring is missing. A Ring 1 agent is now denied a Ring-0-only delete; the same delete from a Ring 0 agent is allowed.

### B4 — Identity is self-asserted; "impossible" rests on an unverified field (Medium, framing)

**Claim attacked:** principle #2, "every agent has a stable cryptographic identity."

The enforcer trusts `req["agent_id"]` and `req["ring"]` verbatim. The decision schema even comments that `agent_id` is a "verifiable per-agent identity, not a shared key," but nothing verifies it. Spoofing the field changes which rules apply. For a dependency-free demo this is expected, but the surrounding narration ("structurally impossible") overreaches: the gate is exactly as trustworthy as the identity feeding it.

**Fix (documented, not code):** the hardened `enforce.py` states the trust assumption in its header, and this is the structural-ASR surface the per-agent-identity principle exists to close. Production binds `agent_id` and `ring` to a verified identity (SPIFFE / DID / mTLS) attested at the gateway before enforcement. Recommend the README make this assumption explicit at the principle-#2 line so the claim is read correctly.

### B5 — The audit chain was an unkeyed checksum: forgeable and truncatable by a writer (High)

**Claim attacked:** principle #3, "tamper-evident audit log," and the build target "cryptographic anchoring (hash chain / Merkle / signed batches)."

`entry_hash` was an unkeyed SHA-256 over the record plus `prev_hash`. The shipped tamper test only covered an in-place edit of one field (which breaks the next link). Two stronger and easier attacks were undetected:

- **Forgery.** An attacker who can write the log edits an entry and recomputes the whole tail. Because the hash is unkeyed, anyone can recompute valid hashes. The "tamper-evident" log is forgeable by exactly the party (the writer) it most needs to defend against.
- **Truncation.** Dropping the last N (incriminating) entries leaves a chain that still verifies perfectly. Nothing committed to the expected length or a signed head, so deletion of the most recent records was invisible.

**PoC (as-shipped code):**
```
honest chain verifies:                       (True, None)
forged (edit + recompute tail) verifies:     (True, None)   # tamper undetected
truncated (dropped last 2 entries) verifies: (True, None)   # deletion undetected
```

**Fix (applied):** the chain is keyed (HMAC under an audit key the log writer does not hold), and the head is sealed over `(length, last hash)` so truncation and extension break the seal. An edit-and-recompute by an attacker without the key is now caught at the chain level; truncation is caught at the head seal. The honest limit is stated in the demo: an attacker who *also* holds the key is defeated only by the external Merkle-root / RFC3161 anchor already documented in `examples/audit-record.example.json`, which is strictly stronger. The runnable artifact now demonstrates the principle instead of under-delivering against it.

### B6 — The schema validator silently ignored unsupported keywords (Medium)

**Claim attacked:** principle #4, "machine-verify the compiled artifact before it is enforced."

The bundled `validate()` implements a small JSON-Schema subset (type, enum, required, additionalProperties, properties, items). It silently ignored `pattern`, `minimum`, `format`, and friends. A validator advertised as enforcing the schema gives false assurance: if a future policy used `pattern` to forbid `..` in a resource, this validator would pass it unenforced, a fail-open validation. A security validator that ignores constraints it does not understand is worse than no validator, because it reads as coverage.

**Fix (applied):** added `pattern` and `minLength` support (the security-relevant keywords for constraining resources and ids). The subset is still a subset and is now documented as such; the right production answer remains a real JSON-Schema library or the automated-reasoning step the spec already calls for.

### B7 — No canonicalization of action or resource names (Medium)

**Claim attacked:** the breadth of any allow rule.

Matching was exact-string on action with no normalization. Deny-by-default protects unknown variants (a misspelled action falls through to deny), so this is not a deny-bypass, but it makes every **allow** exactly as wide as its sloppiest prefix and as narrow as its exact casing. The deeper governance point: policy correctness depends on perfect string agreement between policy authors and the runtime's action and resource naming, a classic source of real-world bypass (the deny says "transfer," the API calls it "wire"). The B1 fix removes the prefix-widening half. A canonicalization layer (normalize case and encoding, map action aliases to a canonical verb) is recommended before any allow rule is trusted to be exactly as wide as written.

## Strengthening the threat catalog

AGS documents four failure modes (policy gap, identity ambiguity, audit gap, policy drift). The findings sharpen them with concrete, reproduced sub-modes. Recommend folding these into the failure-mode catalog as the named structural-ASR surface:

| AGS failure mode | Concrete sub-mode found | Finding |
|---|---|---|
| Policy gap | Allowed prefix escaped by `..`; exact rule widened to a prefix wildcard | B1 |
| Policy gap | A deny shadowed by an allow ordered before it (order-dependent semantics) | B2 |
| Policy gap | Privilege ring carried but not enforced | B3 |
| Identity ambiguity | Decision trusts a self-asserted, unverified identity field | B4 |
| Audit gap | Unkeyed chain forgeable by the writer; truncation undetected | B5 |
| Policy drift | Validator silently ignores unsupported constraints (fail-open validation) | B6 |
| Policy gap | No action/resource canonicalization; allow width depends on string agreement | B7 |

## The narrowed, defensible claim

The thesis is worth keeping, stated precisely. The honest form:

> A denied action is **deterministically** denied: the decision is made in application code, outside the model, so no prompt or chain of reasoning can talk the gate into allowing it. That guarantee holds **given a correct, deny-override, canonicalized policy; an identity verified before enforcement; and an externally-anchored audit log.** Those three are the structural-ASR surface that remains after the model leaves the decision path, and they are exactly what AGS principles #1 to #5 exist to make small.

"Structurally impossible" is true of the model-in-the-loop bypass (the thing prompt-layer safety fails at) and is the right banner. The fixed enforcer now backs it; the three preconditions above are what a buyer should verify, and are the questions the README already tells buyers to ask.

## Pre-launch notes (outside red-team scope, flagged)

- **`examples/privilege-rings.md` uses real internal product and agent names** (the worked fleet references specific internal agents and tenants). Spine public materials are meant to keep illustrations vendor-neutral. Recommend a scrub to generic names before AGS goes public. Not changed here (content/positioning decision).
- **Audit key handling.** `enforce.py` now warns when run with the public reference key. Production must hold `AGS_AUDIT_KEY` in an HSM/KMS and anchor the Merkle root externally, per `audit-record.example.json`.

## Verification

```
python3 examples/enforce.py                 # exit 0: deny-by-default, ring + deny-override
                                            # + traversal blocked; audit catches edit/forge/truncation
```

The hardened enforcer demonstrates four structural guarantees (external email denied, Ring 1 blocked from a Ring 0 action, deny overrides a broad allow, traversal blocked) and survives the full audit attacker battery, where the as-shipped version was bypassable on B1, B2, B3, and B5.
